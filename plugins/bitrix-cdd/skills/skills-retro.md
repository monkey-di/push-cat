# Ретроспектива скиллов data-requirements-analyzer и page-implementer

По итогам реализации главной страницы alexthai (июнь 2026). Фиксирую, что в процессе пошло не так, какие правки пользователя этого бы не потребовали, и какие формулировки в скиллах это предотвращают. Цель: следующая страница (каталог, о компании, контакты) собирается с меньшим числом итоговых правок.

## Сводка фактических переделок за сессию

1. page_sections (общий инфоблок, элементы по магическим кодам main-banner, quick-search, main-articles) переделан на singleton main_page + инфоблок locations. Прямая претензия пользователя: контент страницы должен лежать в singleton-инфоблоке страницы, а не выбираться по строковым кодам из общей свалки.
2. Переключатель блока статей сначала был реализован комментированием вызова в index.php, затем через активность элемента, и только с третьего захода стал явным полем-чекбоксом. Претензия: активность элемента как переключатель контринтуитивна для контентщика.
3. Тяжёлые картинки страницы (слайды регионов 700+ КБ, передний план баннера 1.4 МБ png) остались статикой вёрстки и всплыли в PageSpeed. Переехали в инфоблоки, где библиотека отдаёт их с ресайзом и webp.
4. Превью медиа грузили оригиналы (1104x641 в ячейку 70px) - в библиотеке не было ресайза, добавлен опцией resize в полях. Конфиги пришлось дополнять задним числом.
5. Локации были захардкожены в трёх местах (слайды, фильтр realty.slider, значения списка LOCATION) - сведены к инфоблоку locations как единому источнику.
6. Серия багфиксов поведения JS вёрстки: app.js рассчитан на один попап отзыва на страницу (Swiper падал с null), обработчики a.popup гасят всплытие (return false), filter-select чисто декоративный. Каждое выяснялось по факту бага на staging.
7. CSS-оверрайды компонентов дважды переделывались: страничный бандл грузится раньше app.min.css (нужен префикс body), затем body-селекторы перебили мобильные стили вёрстки (нужно заворачивать в @media min-width 1280px).
8. A11y-правки постфактум по PageSpeed: иконочные кнопки и ссылки без имени, ссылка с label, скрытым на мобильных (display:none выкидывает текст из a11y-дерева).
9. Inputmask вёрстки блокирует вставку в телефонные поля (preventDefault на paste) - перекрыт своим скриптом после бандла.

## data-requirements-analyzer

### Проблема 1: нет правила "singleton на страницу"

Скилл позволил спроектировать общий инфоблок "Контент страниц" с элементами по фиксированным кодам. page-implementer при этом прямо требует страничные синглтоны (home_page, about_page) - скиллы противоречат друг другу, а анализатор отрабатывает раньше и его результат фиксируется в data-model.

Предлагаемая правка (в раздел "Алгоритм работы", шаг 1, и в чек-лист):

- Уникальный контент страницы (баннеры, подзаголовки, картинки секций, переключатели блоков) - это ОДИН singleton-инфоблок этой страницы с одним элементом, контент полями (BANNER_IMAGE, QUICKSEARCH_TITLE...). Запрещено: общий инфоблок "секций" с элементами, выбираемыми по строковому коду; компонент не должен искать элемент по магической строке.
- Повторяющиеся однотипные сущности (карточки, слайды, локации) - отдельные инфоблоки-коллекции, в singleton они не лезут.
- В чек-лист: "Контент каждой страницы собран в её singleton; ни один компонент не ищет элемент по магическому коду".

### Проблема 2: переключатели видимости

Паттерн "Секции с управлением видимостью" предлагает SECTION_SHOW, type L, values Да/Нет. Сейчас в BitrixCdd есть list_type C: список с единственным значением Да отображается одиночным чекбоксом - это очевиднее для менеджера, чем выпадашка Да/Нет, и пустое значение естественно означает "выключено".

Предлагаемая правка (references/patterns.md, паттерн видимости):

```
ТЗ: "Блок скрыт по умолчанию" / "блок можно скрыть в админке"
-> Поле в singleton страницы: SHOW_SECTIONNAME, type: 'L', list_type: 'C', values: ['Да']
-> Демо: чекбокс не взведён, если по ТЗ блок скрыт по умолчанию
-> ЗАПРЕЩЕНО реализовывать переключение комментированием кода или активностью элемента
```

### Проблема 3: критерий редактируемости слишком жёсткий для изображений

Правило "нет явного маркера в ТЗ - контент статический, полей не нужно" привело к тому, что слайды регионов и передний план баннера остались файлами вёрстки. Для текстов и мелких элементов правило верное, но крупные изображения - особый случай: в инфоблоке они автоматически получают ресайз и webp, а статикой улетают в PageSpeed как есть (у нас 1.4 МБ png и три jpg по 700 КБ).

Предлагаемая правка (раздел "Критерий редактируемости", добавить исключение):

- Исключение: контентные изображения секций (фоны баннеров, слайды, иллюстрации блоков) заводятся файловыми полями даже без маркера редактируемости. Причина не в редактируемости, а в пайплайне отдачи: файлы из инфоблоков отдаются с resize и webp-конвертацией, статика вёрстки - как есть. Статикой остаются только иконки, svg, логотипы, мобильные подмены в picture и фоны из css.

### Проблема 4: доменные справочники не выделяются

Локации фигурировали в ТЗ трижды (слайды регионов 5.1.2, фильтр ленты 5.1.3, переходы в каталог с фильтром), но справочником не стали - значения разъехались по хардкоду компонента, значениям списка и статичным слайдам.

Предлагаемая правка (шаг 1 "Идентификация сущностей"):

- Если одна и та же сущность упоминается в нескольких блоках ТЗ (как фильтр, как слайд, как параметр перехода) - это доменный справочник: отдельный инфоблок, CODE элемента = url-код для фильтров и переходов (?location=phuket). Маркеры: "по выбору X лента обновляется", "переход в каталог с фильтром по X", повторяющийся список значений в разных секциях.
- В чек-лист: "Значения, используемые в фильтрах/переходах, не захардкожены и не размножены - есть инфоблок-справочник".

### Проблема 5: файловые поля без параметров отдачи

Скилл описывает file_type и пропорции, но не размер отдачи. Из-за этого превью грузили оригиналы.

Предлагаемая правка (таблица "Типы полей", строка F):

- Для каждого файлового поля с изображениями указывать resize по фактическому слоту вёрстки (ширина слота x2 под retina, вписывание пропорциональное): `'resize' => ['width' => W, 'height' => H]`. Если у поля два потребителя (превью + попап/галерея), превью берёт само поле, попап - FIELD_ORIGINAL. Размер слота брать из вёрстки/css, не выдумывать.

## page-implementer

### Проблема 6: анализ вёрстки не покрывает JS-поведение

markup-analyzer описывает структуру секций, но не поведение app.js. Все болезненные баги сессии (один попап на страницу, return false на a.popup, декоративный filter-select, порядок инициализации слайдеров) обнаруживались по факту на staging.

Предлагаемая правка: НЕ дописывать это в markup-analyzer, а вынести в два новых скилла (см. раздел "Два новых скилла перед page-implementer" ниже). markup-analyzer остаётся строго структурным экстрактором страницы: секции, данные, повторяющиеся блоки. Глобальные ограничения вёрстки он берёт из артефакта аудита, расхождения с ТЗ - из артефакта gap-анализа.

### Проблема 7: CSS-каскад не описан

Две итерации правок оверрайдов из-за порядка бандлов.

Предлагаемая правка (references/component-patterns.md или "Критические правила"):

- Страничные css-бандлы Битрикса подключаются РАНЬШЕ css шаблона (app.min.css). Оверрайды в style.css компонента писать с повышением специфичности префиксом body; десктопные оверрайды заворачивать в @media (min-width: 1280px), иначе они перебьют мобильные медиа-правила вёрстки.

### Проблема 8: a11y не входит в перенос вёрстки

Вёрстка не содержит aria-атрибутов, и шаблоны унаследовали это. Правилось постфактум по двум прогонам PageSpeed.

Предлагаемая правка ("Из вёрстки (ОБЯЗАТЕЛЬНО)" + чек-лист Фазы 4):

- При переносе вёрстки иконочные кнопки и ссылки (svg/img без текста) получают aria-label; логотипы - содержательный alt; если видимый текст элемента скрывается css на каком-то брейкпоинте (display:none у .label) - имя задаётся aria-label явно. Декоративные изображения при текстовом соседе - alt="" (это корректно, не флагуется).
- В Фазу 4 пункт валидации: "на странице нет button/a без доступного имени" (проверяется грепом по собранному html: элементы без текста, aria-label и img[alt]).

### Проблема 9: namespace компонентов захардкожен

Скилл предписывает custom:component.name, проект использует FSD-слои (pages:, widgets:, entities:, features:, shared). Расхождение со сложившейся структурой.

Предлагаемая правка (раздел "Именование"):

- Namespace компонентов брать из структуры проекта (посмотреть local/components/), а не навязывать custom:. Если структуры ещё нет - предложить FSD-разбиение: pages (уникальные блоки страниц), widgets (общие структурные: шапка, подвал, попапы, слайдеры), entities (карточки сущностей), features (формы/избранное), shared.

### Проблема 10: жизненный цикл не закрывается деплоем и проверкой

Фаза 4 валидирует связность файлов, но не живую страницу. Почти все находки сессии (intrinsic size, битые попапы, каскад) видны только на работающем staging.

Предлагаемая правка (Фаза 4):

- php -l на все созданные/изменённые php-файлы.
- После деплоя: curl страницы и проверка, что картинки уходят с resize-путей (а не оригиналы), блоки с переключателями реагируют на поле, фильтры с url-параметрами фильтруют выдачу. Если проект деплоится через CI - дождаться рана и сделать первый хит (синк инфоблоков срабатывает на нём).

### Проблема 11: режим синхронизации и фиксация решений

Выработанные в сессии процессные вещи в скилле отсутствуют.

Предлагаемая правка ("Из архитектуры проекта"):

- На этапе разработки (нет ручного контента) sync_mode 'once' + bump version при каждом изменении demo_data; инфоблоки с боевыми данными (заявки) - всегда 'soft'. Перед передачей контентщикам вернуть once -> soft/ensure.
- Архитектурные решения фиксировать в .context/decisions.md (нумерованные пункты, на них ссылаются комментарии в коде), отложенное и несоответствия вёрстке/ТЗ - в techdebt.md с разделением "отложено осознанно" / "работает не так". Скилл должен дописывать эти файлы, а не держать решения в чате.

## Два новых скилла перед page-implementer

Аудит вёрстки и сверка её с бизнес-логикой - разные вопросы с разной периодичностью, разделяем на два скилла. Оба пишут межконтекстные артефакты в .context/ - результаты переживают компакты и сессии, page-implementer потребляет их вместо повторного анализа.

### layout-auditor (разовый, на поставку вёрстки)

Вопрос: "как вёрстка устроена и где она кривая сама по себе". Не привязан к ТЗ, универсален для любого проекта с готовой вёрсткой. Запускается при получении или обновлении вёрстки, артефакт - .context/layout-audit.md.

Содержимое аудита:
- Карта поведения JS: какие обработчики на какие классы/якоря вешаются, что гасит всплытие (return false / stopPropagation - свои слушатели только в capture-фазе), какие блоки рассчитаны ровно на один экземпляр на страницу (попапы и слайдеры с фиксированными id), какие контролы декоративные (открывают/закрывают, но выбор ничего не делает).
- Каскад и сборка: порядок подключения бандлов, что грузится раньше страничных стилей, правила для оверрайдов.
- Анти-паттерны: preventDefault на paste (маски ввода), изображения кратно больше контейнеров, z-index-конфликты, тяжёлые ассеты без современных форматов.
- A11y-дыры: иконочные контролы без имён, пустые alt, текст, скрываемый css на брейкпоинтах.
- Что не чинится сразу - сразу засеивается в techdebt.md.

### layout-spec-gap (динамический, перед имплементацией каждой страницы)

Вопрос: "где реализация верстальщика расходится с бизнес-логикой, как она ДОЛЖНА быть реализована по ТЗ". На входе: ТЗ страницы, вёрстка, паспорт аудита. Артефакт - .context/gap-{page}.md, входит в план page-implementer, чтобы план сразу учитывал, что дописывается поверх вёрстки.

Типы расхождений (все - реальные находки этой сессии, аудитом не ловятся, потому что сами по себе не баги):
- Декоративный контрол, которому ТЗ предписывает поведение: filter-select открывается/закрывается честно, но ТЗ 5.1.3 требует, чтобы выбор локации фильтровал ленту.
- Структурное ограничение вёрстки против данных: один попап #feedback1 валиден, пока отзыв один; при N отзывах из инфоблока ломается Swiper.
- Поведение, противоречащее ТЗ: кнопки "В каталог" ведут на голый /catalog/, ТЗ 5.1.2/5.1.6 требуют переход с предвыбранным фильтром; маска телефона +7 при тайском рынке.
- Элемент, требуемый ТЗ, в вёрстке отсутствует: половинчатая звезда рейтинга, окно "Оставить заявку" с привязкой к объекту.

Каждое расхождение классифицируется: реализуем поверх вёрстки бекендом/JS - правка вёрстки (верстальщику или своим оверрайдом, в techdebt) - откладываем осознанно (в techdebt с причиной).

### Связка с page-implementer

page-implementer в Фазе 1 проверяет артефакты: нет layout-audit.md или вёрстка свежее него - требует прогнать layout-auditor; нет gap-файла страницы - требует layout-spec-gap. Работать вслепую отказывается, порядок вызова не держится в голове.

### Замечание без правки

Требование "Demo data = вёрстка 1:1" отработало хорошо, как и параллельная схема анализа. Сломалось то, что в скиллах не было зафиксировано, а держалось на устных решениях в сессии - ровно это и переносим в формулировки.
